## Session summary
The user is hardening UltraWinBar (fork of RetroBar, WPF .NET 6, ManagedShell 0.0.358, up to four panels) for arbitrary uptimes; release 2.2.0 is published (tag v2.2.0, commit d97b920) and the previous checkpoint is 92050ef.
This session ran audit round 5 (/oxx, investigation only, no code changes) and recorded its findings as tasks #55–#63 per the user's request.
The round combined a full read of the source tree with live read-only measurements on the installed build (PID 27092, watchdog PID 16072, about 45 minutes of uptime): handles stable near 790, 17–18 threads, GDI 55, USER 63, CPU 0.5–1%, UI thread ~660–680 context switches/s in two 60 s samples.
A 90 s dotnet-trace (dotnet-sampled-thread-time) showed our own code at a fraction of a percent; UI-thread time goes to ManagedShell (ExplorerHelper 100 ms TaskbarMonitor_Tick, TasksService.ShellWinProc → addWindow sanity checks), WPF render/layout (including AutomationPeer.UpdateSubtree from an external UIA client), mouse input and dispatcher timers; logging cost was negligible.
Passive harnesses measured system WinEvents (our permanent hooks see ~2/s) and shell-hook traffic (~24/s, almost all from msrdc hidden RemoteApp windows, likely WSLg); most of the ~680 wakeups/s remain unattributed (WPF plus external messages).
A first shell-hook harness spun at high CPU because of per-message Process.GetProcessById; it was stopped by its own PID (24876) and replaced with a lean version.
ManagedShell master sources (TasksService.cs, ApplicationWindow.cs) were read from GitHub: the hypothesis that dead windows accumulate in the task collection was not confirmed.
All temporary measurement files in .claude/scratch were deleted; the working tree is clean apart from this checkpoint.
Round 5 findings are code-confirmed except #59's visible effect (mechanism confirmed, not reproduced) and #55's duplicate balloon popup (mechanism from code, needs a manual test).
No /loop or /babysit timers are active.
