# Ревью раунда 6: работа с памятью, надёжность, сложность, архитектура

Дата: 2026-09-28. Код: `master` на `5b7b3f4` (2.2.13), ManagedShell 0.0.358
(коммит `b4521b2`).

## 1. Зачем и как

Поводом стало падение 07:20:42. После 7 часов работы процесс завершился с
`AccessViolationException`. Разбор дампа показал запись 8 байт по мусорному
указателю в COM-подписчике ManagedShell: в `IAppVisibilityEvents` нет
`[PreserveSig]` (исправлено в `5b7b3f4`). Задача этого ревью — найти другие
ошибки того же рода и шире: неверную работу с памятью, утечки, лишнюю
сложность. Главное — классы багов, которые можно закрыть принципиально,
рефакторингом, а не точечными правками.

Что проверено:

- **Interop нашего кода.** Все `DllImport` (51 объявление в 11 файлах),
  все `[ComImport]`-интерфейсы (15), все делегаты, которые уходят в native
  (8 мест), все классы, которые сами реализуют COM-интерфейсы.
- **ManagedShell** на коммите `b4521b2`, только в тех путях, которые мы
  используем. Проверены COM-объявления, разбор `WM_COPYDATA` трея, владение
  `HICON`, таймеры, колбэки.
- **Время жизни объектов.** 92 места подписки (`+=`), подписки на
  статические события и синглтоны, таймеры, кэши по `hwnd`, освобождение RCW,
  потоки.
- **Горячие пути.** Сортировки, фильтры, работа на каждое событие, поллинг.
- **История.** 85 коммитов с начала сентября сведены в классы багов.

Исходные замеры из раунда 5. Handles около 790 и не растут, GDI 55, USER 63,
CPU 0,5–1 %. Наш код занимает доли процента времени UI-потока. Основные
потребители — таймеры ManagedShell, WPF-рендер и внешние UIA-клиенты. Поэтому
пункты про сложность ниже касаются масштабируемости и аллокаций. Текущий CPU
они почти не меняют.

## 2. Коротко

1. **Самый опасный класс — сигнатуры interop.** Падение показало, что
   неправильно объявленный COM-метод незаметно портит память и через часы
   роняет процесс. Выборочно проверять это бесполезно, нужен механический
   запрет. Предлагается тест-сторож, который проверяет все COM-объявления по
   правилам (раздел К1). У нас нашлись ещё два места этого класса:
   `DesktopActions` и `IImmersive*`. Они пока не падают, но корректны только
   случайно.
2. **Нативные колбэки без барьера исключений.** Исключение из колбэка
   WinEvent сейчас гарантированно убивает процесс мимо
   `DispatcherUnhandledException`. Нужна одна обёртка для всех хуков и
   колбэков (К2).
3. **Утечки через подписки лечились в раундах 2–5 точечно, шесть раз.**
   Структурное решение: слабые подписки на синглтоны с фильтром по свойству
   плюс одна область жизни (lifetime scope) на контрол (К3).
4. **Восстановление после перезапуска Explorer реализовано пятью разными
   способами** в пяти компонентах. Нужен один владелец COM-объектов Explorer
   (К4).
5. **ManagedShell — непроверяемая зависимость с реальными дефектами.** Там
   COM-подписчик, VARIANT_BOOL вместо BOOL, `WM_COPYDATA` без проверки
   размера, `DestroyIcon` чужих иконок, три таймера по 100 мс на UI-потоке.
   Требуется решение: форк или вендоринг либо список запрещённых API (К8).
6. **Наблюдаемость.** Падение не оставило ни строки в нашем логе. Нужны
   глобальные обработчики, периодическая строка «здоровья» и дампы (К9).

## 3. Находки по классам

### К1. Сигнатуры interop и безопасность памяти

**История.** Падение 07:20:42: `IAppVisibilityEvents` без `[PreserveSig]`
(исправлено в `5b7b3f4`).

**Правило, которое нарушается.** Если у метода `[ComImport]`-интерфейса нет
`[PreserveSig]`, .NET переписывает его сигнатуру. Возвращаемое значение
становится скрытым параметром `[out, retval]` (указатель), а HRESULT
превращается в исключение. Последствия зависят от направления вызова:

- **Мы вызываем COM** (RCW). Лишний указатель native-код игнорирует. Память
  не портится, но проверки вида `hr != 0` становятся мёртвым кодом: ошибки
  приходят исключениями.
- **Нас вызывают** (CCW, подписчики и синки). .NET пишет результат по
  скрытому указателю, которого native-код не передавал. Это запись по
  мусорному адресу, то есть наше падение.
- **`bool` в COM-интерфейсах по умолчанию маршалится как `VARIANT_BOOL`**
  (2 байта), а в P/Invoke — как `BOOL` (4 байта). API Windows почти всегда
  пишут `BOOL`. Получается запись 4 байт в 2-байтовый буфер заглушки
  маршалинга.

**Найдено в нашем коде:**

| Место | Проблема | Вызывается сейчас? | Риск |
|---|---|---|---|
| `Core/Desktop/DesktopActions.cs`, `IManager.CanViewMoveDesktops`, `IPins.IsAppIdPinned` | `bool` без `[return: MarshalAs(UnmanagedType.Bool)]`: native пишет `BOOL*` (4 байта) в `VARIANT_BOOL` (2 байта) | Да. `IsAppIdPinned` вызывается при каждом восстановлении pins и в меню | Скрытая порча стека заглушки. Сейчас её маскирует выравнивание слотов JIT, и это никто не гарантирует |
| `Core/Windows/StartMenuMonitor.cs`, `IImmersiveMonitor`, `IImmersiveMonitorManager`, `IImmersiveLauncher_*` | Все методы без `[PreserveSig]`; `out bool` (`IsVisible`, `IsConnected`, `IsPrimary`, `IsEqual`) как `VARIANT_BOOL` | Методы с `out bool` не вызываются. `ShowStartView`, `ConnectToMonitor`, `GetFromHandle` вызываются, и их проверки `!= 0` — мёртвый код | Ловушка: первый же вызов `IsVisible` даст запись мимо буфера |
| `Core/Input/LowLevelMouseHook.cs`, `CallNextHookEx`, `LowLevelMouseProcDelegate` | `WPARAM` объявлен как `uint`, а он размером с указатель | Да | Работает, потому что сообщения мыши помещаются в 32 бита. Тип неверный |
| Дубли объявлений | `SetWinEventHook` и `UnhookWinEvent` объявлены 4 раза с разными типами делегатов; `GetWindowThreadProcessId` 3 раза в двух вариантах сигнатуры; `GetClassName`, `GetForegroundWindow`, `GetAncestor` по 2 раза; плюс свои версии у ManagedShell через `using static` | — | Правка сигнатуры в одном месте не доходит до остальных |

Проверено и корректно: `VirtualDesktopContext.IDesktopManager`,
`LauncherVisibility`, `DesktopActions.IView`/`IViews` (vtable совпадает с
Windows 10 19041–19045), структуры `GUITHREADINFO`, `MSG`, `MSLLHOOKSTRUCT`,
размеры буферов у `GetClassName`, `GetUserDefaultLocaleName`,
`DwmGetWindowAttribute` и `RegQueryValueEx`. `ClockFlyoutLauncher` использует
in-proc сервер (`timedate.cpl`), поэтому его кэш не протухает после
перезапуска Explorer.

**Структурное решение.**

1. **Тест-сторож interop** (рефлексия по сборке `UltraWinBar`). Для каждого
   `[ComImport]`-интерфейса:
   - у каждого метода есть `[PreserveSig]` и возврат `int` или `void`;
   - у каждого `bool`-параметра и возврата явно указан `MarshalAs`;
   - интерфейс, который реализует управляемый класс (CCW), обязан пройти обе
     проверки без исключений.

   Для `DllImport`: параметры с именами `hwnd`, `wParam`, `lParam`, `lResult`,
   `hWnd*` и `h*` (дескрипторы) имеют тип `IntPtr`, `UIntPtr` или `nint`.
   Отдельный список запрещённых API ManagedShell с известными дефектами
   (`AppVisibilityHelper`, `IAppVisibility*`) и проверка, что наш код их не
   использует. Так весь класс ловится при сборке и тестах, без ревью глазами.
2. **Один слой interop.** `Core/Interop/` с файлами по DLL (`User32.cs`,
   `Dwmapi.cs`, `ShellCom.cs`) без дублей. `using static
   ManagedShell.Interop.NativeMethods` только там, где его сигнатуры проверены.
3. **Перспектива.** Если откажемся от цели `net6.0-windows` (это
   Windows 7/8; решение за владельцем проекта), можно перейти на
   `LibraryImport` и `[GeneratedComInterface]` с
   `[assembly: DisableRuntimeMarshalling]`. Маршалинг станет сгенерированным
   кодом, который видно и который проверяют анализаторы; неявных преобразований
   сигнатур не будет.

### К2. Нативные колбэки: время жизни, поток, исключения

**История.** Незакорнённый делегат хука мыши (исправлено в `8d2903d`). Хук,
оставшийся после закрытия панели (там же). Ранее: перенос хука на отдельный
поток и установка хука меню только на время позиционирования.

**Найдено.** Исключение, вылетевшее из колбэка WinEvent или хука, проходит
через кадры `user32` и не попадает в `DispatcherUnhandledException`. На
.NET 9 и новее это завершение процесса. Барьера `try/catch` нет в:

- `TaskWindowRecovery.OnCloakChanged`;
- `WindowPlacementGuard.OnWindowEvent`, откуда вызывается
  `requestWorkAreaRecovery`;
- `StartMenuMonitor.ForegroundEventProc` и `MenuEventProc`. Отсюда цепочка
  `setVisibility` → `StartMenuVisibilityChanged` → UI кнопки Start → ресурсы
  и раскладка. Любая ошибка в этом UI-коде становится падением, а не строкой
  в логе;
- колбэке `RegistryWatch` в `ThreadPool` и лямбде `EnumWindows` в
  `WorkAreaManager`. Здесь риск низкий: код простой.

Барьер уже есть в `DesktopActivationGuard.OnForeground`,
`LowLevelMouseHook.MouseHookProc` и `LauncherVisibility.Sink`.

Ещё одно слабое место: `async void UpdateCheck_Elapsed` на
`System.Timers.Timer` (`Updater`). Сейчас исключения ловятся внутри
`CheckForUpdate`, но это держится только на дисциплине.

**Структурное решение.** Единый примитив `WinEventHook` / `NativeHook`, через
который проходят все хуки и колбэки:

- делегат закорнён на всё время установки;
- установка и снятие проверяют поток-владелец (`Dispatcher.CheckAccess`);
- пользовательский обработчик обёрнут в `try/catch` с логом и, по
  необходимости, передаётся в dispatcher;
- в реестре хуков виден их счётчик для строки «здоровья» (К9).

Четыре текущие реализации WinEvent-хуков сворачиваются в одну. Тест проверяет,
что в сборке нет прямых вызовов `SetWinEventHook` и `SetWindowsHookEx` вне
примитива.

### К3. Подписки и время жизни UI-объектов

**История.** Шесть точечных исправлений в раундах 2–5:

- `InvertEffect` через статическое событие удерживал эффекты;
- повторный `Loaded` у кнопок задач создавал дубли подписок;
- `ListCollectionView` над живущими весь процесс коллекциями удерживали
  панели (дважды);
- скрытые списки трея держали view и подписанные иконки (`e4c0c57`);
- хуки перетаскивания оставались после закрытия панели.

**Состояние.** 92 места подписки. 18 классов подписываются на
`Settings.Instance.PropertyChanged`. Из них 8 контролов живут в каждой панели,
а `TaskButton` — на каждое окно. На `VirtualDesktopContext.Instance.Changed`
подписаны `TaskList` и каждая `TaskButton`. Во всех контролах одна и та же
ручная схема: флаг `_isLoaded`, `+=` в `Loaded`, `-=` в `Unloaded`. Сейчас всё
сбалансировано, это проверено по файлам. Но баланс держится на дисциплине, а
каждая пропущенная отписка — утечка панели целиком, потому что синглтон
держит её сильной ссылкой.

**Структурное решение.**

1. **Слабые подписки с фильтром по свойству** на всё, что живёт весь процесс:
   `Settings`, `VirtualDesktopContext`, `ExplorerMonitor`. Для `Settings`
   подходит штатный `PropertyChangedEventManager.AddHandler(source, handler,
   propertyName)`, для остального — `WeakEventManager<TSource, TArgs>`.
   Утечка через забытую отписку становится невозможной. Заодно обработчик
   вызывается только для своего свойства, а не каждый раз для каждого
   изменения с `if (e.PropertyName == …)`.
2. **Область жизни контрола.** Прикреплённое поведение или базовый хелпер
   `Lifetime.Attach(control, scope => { scope.Subscribe(...); scope.Timer(...); })`:
   подписки и таймеры активны между `Loaded` и `Unloaded` или закрытием окна и
   снимаются автоматически. Шаблон с `_isLoaded` уходит из 11 файлов.
3. **Тест утечек.** Существующий `OwnerStaysReachable` проверяет
   синтетический view. Нужно расширить его на настоящие компоненты: создать и
   закрыть панель N раз, выполнить `GC`, проверить через `WeakReference`, что
   панели, `TaskList` и `TaskButton` собраны.

### К4. COM-объекты Explorer и восстановление после его перезапуска

**История.** Раунды 3–5: «Keep retrying shell COM objects after Explorer
restarts», «Recreate shell COM objects after Explorer restarts», сброс кэша
launcher (`d50d3b2`), возврат менеджера рабочих столов (`ManagerRecovered`),
пересоздание `AppVisibility`.

**Состояние.** Пять компонентов держат прокси Explorer и восстанавливают их
каждый по-своему:

- `StartMenuMonitor`: `AppVisibility` с откатом 2/5/15/60 с, кэш launcher,
  сброс по `ExplorerRestarted` и по `COMException`;
- `VirtualDesktopContext`: менеджер с собственным откатом и `ManagerRecovered`;
- `DesktopActions`: создаётся заново на каждую операцию;
- `ImmersiveShellHelper.GetImmersiveShell()`: новый объект на каждый вызов,
  RCW не освобождаются явно;
- `ClockFlyoutLauncher`: in-proc, к этому классу не относится.

Проверка «прокси отвалился» (`IsDisconnected` / `IsComDisconnected`)
реализована дважды.

**Структурное решение.** Сервис `ShellSession` — единственный владелец
COM-объектов, которые живут в Explorer.

- API: `Get<T>()`, `Invalidate()` и событие `Reconnected`.
- Одна политика отката, одна проверка HRESULT «отвалился».
- `Invalidate` вызывается при `ExplorerRestarted` или при первом
  disconnect-HRESULT и сбрасывает всё сразу.
- Компоненты не кэшируют RCW сами, а берут их у сессии.

Весь класс «протухший прокси после перезапуска Explorer» закрывается в одном
месте, и его покрывает один тест.

### К5. Петли обратной связи и штормы обновлений

**История.**

- бесконечный цикл обновления TaskOrder;
- петли «рабочая область ↔ размещение окон»;
- перестройка всех списков на каждую активацию окна;
- переоткрытие панелей на каждое изменение настройки (исправлено в
  `226f312`);
- повторная загрузка темы System на каждую рассылку.

**Состояние.** Каждое такое место чинили своим механизмом:
`QueueViewRefresh` с флагом, откат `WorkAreaRecovery`, склейка
переоткрытий, дебаунс сериализации настроек, фильтр рассылок.

**Структурное решение.**

1. Общий примитив склейки `Coalescer` (флаг «грязно» плюс одна операция
   dispatcher с приоритетом) вместо самодельных флагов.
2. Однонаправленный поток данных: изменение настроек → один раз вычисленное
   производное состояние → представления. Правило: обработчик
   `Settings.PropertyChanged` не пишет в `Settings`. Его проверяет
   reentrancy-guard в `SettingsManager`, который в Debug-сборке падает, а в
   Release пишет предупреждение.

### К6. Потоки и блокирующие вызовы

**История.** Блокирующий `SendMessage` в `JapaneseIme` (исправлено в
`5128041`). Перенос хука мыши на отдельный поток.

**Состояние.**

- Модель потоков неявная. Callback `IAppVisibilityEvents` приходит на
  рабочем потоке оболочки, WinEvent — на потоке установки, `RegistryWatch` —
  в `ThreadPool`, рассылка — в `Task.Run`, `Updater` — на таймере пула.
- Межпроцессные COM-вызовы в Explorer идут с UI-потока (STA): менеджер
  рабочих столов, `DesktopActions`, launcher. Пока STA ждёт исходящий вызов,
  COM прокачивает сообщения. Поэтому посреди, например,
  `PersistentDesktopPins.Restore` могут выполниться колбэки WinEvent, таймеры
  и ввод. Это источник трудноуловимой реентерабельности. Прямых
  доказательств такого бага сейчас нет, но это известный класс проблем.

**Структурное решение.**

1. Зафиксировать модель потоков. Всё состояние принадлежит UI-потоку;
   фоновые колбэки только передают работу в dispatcher. Методы, которые
   меняют состояние, проверяют поток через `Debug.Assert`.
2. Среднесрочно, и только если появятся свидетельства реентерабельности:
   отдельный STA-поток для COM-вызовов в Explorer с тайм-аутами. UI отправляет
   запросы и ждёт результат асинхронно. Если Explorer завис, UI-поток не
   блокируется. Это крупное изменение, делать его заранее не рекомендую.

Таймеры ManagedShell без форка не заменить (К8). Этот пункт совпадает с

### К8. ManagedShell как чёрный ящик

Найдено в ManagedShell `b4521b2` (0.0.358):

- `IAppVisibilityEvents` без `[PreserveSig]` — причина падения. Мы обошли
  его своим `LauncherVisibility`.
- `IAppVisibility.IsLauncherVisible(out bool)` как `VARIANT_BOOL`: при каждом
  опросе запись 4 байт в 2-байтовый буфер. У нас было до 10 вызовов в
  секунду; после `5b7b3f4` не используется.
- `TrayService.WndProc`, `WM_COPYDATA`: для `dwData = 1` (`SHELLTRAYDATA`) и
  `dwData = 3` (`WINNOTIFYICONIDENTIFIER`) не проверяется `cbData`, после чего
  выполняется `Marshal.PtrToStructure`. Проверка есть только для AppBar
  (`dwData = 0`). Любой процесс может прислать нашему `Shell_TrayWnd`
  короткий буфер, и мы прочитаем за его пределами. Возможно чтение из
  недоступной памяти, то есть падение. `shell32` сам всегда шлёт буфер
  полного размера, так что риск исходит от сторонних и сломанных программ.
- `IconImageConverter.GetImageFromHIcon` всегда вызывает `DestroyIcon` на
  переданном `HICON`, в том числе на чужих: полученных через `WM_GETICON`,
  `GetClassLongPtr`, `Shell_NotifyIcon`. Для чужих процессов вызов просто
  завершается ошибкой. Для окон нашего процесса он уничтожает иконку окна у
  WPF. Владение иконками не определено.
- `ITrayNotify.EnableAutoTray(bool)` и `DoAction(bool)` передают
  `VARIANT_BOOL` там, где ожидается `BOOL`. На практике безвредно, но
  неверно.
- Методы `IShellItem`, `IShellItemImageFactory`, `IServiceProvider` и других
  интерфейсов объявлены как `int X()` без `[PreserveSig]`. Их вызывают только
  со стороны RCW, поэтому память не портится, но коды ошибок не видны.
- Три таймера по 100 мс на UI-потоке (К7).
- `ApplicationWindow.WinFileName` при пустом результате (защищённые процессы)
  заново запрашивает путь при каждом обращении.

**Решение нужно от владельца проекта.**

- **Вариант A (рекомендую): форк или вендоринг ManagedShell.** Подмодуль или
  проектная ссылка на форк от `b4521b2`, та же версия, без обновления.
  Исправить перечисленное у источника, в том числе убрать таймеры, прогнать
  по нему тот же тест-сторож из К1 и отправить PR в upstream. Минусы:
  поддержка форка и ребейзы на новые версии.
- **Вариант B: оставить NuGet.** Список запрещённых API плюс тест (К1),
  обёртки на нашей стороне там, где это возможно. Дефект разбора
  `WM_COPYDATA` и таймеры снаружи не исправить.

### К9. Наблюдаемость

**История.** Падение 07:20:42 не оставило в нашем логе ничего. Причину
удалось восстановить только по дампу из `%LOCALAPPDATA%\CrashDumps`.

**Состояние.** Обрабатывается только `DispatcherUnhandledException`. Не
подписаны `AppDomain.CurrentDomain.UnhandledException` (смерть от исключения
на фоновом потоке) и `TaskScheduler.UnobservedTaskException`. Сводных
метрик ресурсов в логе нет: утечку при долгом аптайме нельзя увидеть в логах
пользователя без внешних инструментов.

**Структурное решение.**

1. Глобальные обработчики с немедленным сбросом лога на диск.
   `UnobservedTaskException` — залогировать и вызвать `SetObserved`.
2. Строка «здоровья» раз в 15–30 минут на уровне Info. Состав: handles,
   GDI и USER (`GetGuiResources`), потоки, private bytes, размер GC heap,
   число окон в источнике задач, число установленных хуков из реестра К2,
   число подписчиков у `Settings.PropertyChanged`. Утечки станут видны прямо в
   логе пользователя.
3. Дампы. Параметр `LocalDumps` для `UltraWinBar.exe` (HKLM, нужны права
   администратора) — как опция установщика или инструкция в документации.
   На этой машине он уже включён.

### К10. Тесты

**Состояние.** Тестовый проект — одна консольная программа на top-level
statements. `Program.cs` занимает 966 строк при лимите 1000, плюс
`UptimeChecks.cs`. Приватные члены доступны через рефлексию по строковым
именам. Первая упавшая проверка обрывает весь прогон. Переименование в коде
ломает тесты только во время выполнения.

**Структурное решение.** Перейти на xUnit или MSTest:

- доступ к `internal` через `InternalsVisibleTo`, вместо строковой
  рефлексии — проверка компилятором;
- каждая проверка — отдельный тест с понятным отчётом;
- категории «чистые» и «живой рабочий стол» (COM, хуки, окна);
- туда же тест-сторож interop (К1), тесты утечек (К3) и `ShellSession` (К4).

### К11. Размер и связность классов

Файлы у предела в 1000 строк: `Taskbar.xaml.cs` (943), `StartMenuMonitor.cs`
(898), `Settings.cs` (809), `JapaneseIme.xaml.cs` (770),
`DesktopActivationGuard.cs` (709). `StartMenuMonitor` совмещает четыре
обязанности:

1. определение видимости Start: poller, WinEvent, COM-подписчик;
2. размещение и коррекцию меню;
3. COM-интерфейсы launcher;
4. интеграцию с Open-Shell.

Предлагаемое разделение: `StartMenuVisibility`, `StartMenuPlacement` (файл
уже существует, логика расщеплена), `ImmersiveLauncher` (interop, переезжает в
`Core/Interop`) и `OpenShellBridge`. У `Taskbar.xaml.cs` отделить
перетаскивание часов и трея и контекстные меню в partial-файлы, как уже
сделано с `Taskbar.PanelDrag.cs`.

## 4. Сложность (O) и аллокации

| Место | Сейчас | Предлагается |
|---|---|---|
| `TaskListSorter.Compare` | На каждое сравнение `GetTaskOrderForEdge`: два прохода по всему `TaskOrder` (T записей всех краёв и рабочих столов), новый `List<string>`, два `IndexOf`. Сортировка n окон стоит O(n log n · T) и n log n аллокаций, на каждое `Refresh` каждой панели | Словарь рангов `id → index`, строится один раз на сортировку или по версии `TaskOrder`: O(T + n log n), без аллокаций в сравнении |
| `TaskList.Tasks_Filter` → `GetAssignedEdge` | На каждый фильтр каждого окна три идентификатора (legacy через `GetClassName`/`GetWindowText`) и проход по всем назначениям: O(n · A) плюс P/Invoke на каждый `Refresh` | Кэш идентификаторов окна (`ConditionalWeakTable`, сброс при смене заголовка) и индекс назначений `Dictionary<(desktop, mode, id), edge>`: O(n) |
| `NotifyIconList.NotifyIconComparer` | `FindIndex` с лямбдой по `NotifyIconOrder` на каждое сравнение | Словарь рангов, как у задач |
| Рассылка `Settings.PropertyChanged` | Каждое изменение вызывает все обработчики (около 40 + n), каждый сравнивает строки | Подписки с фильтром по свойству (К3): вызываются только нужные |
| `VirtualDesktopContext.Changed` | `TaskButton.UpdatePinnedAppearance` на каждую кнопку: O(n · P) по списку pins | Множество закреплённых идентификаторов на рабочий стол, считается один раз: O(n + P) |
| `WindowPlacementGuard` | `Application.Current.Windows` (копия коллекции) дважды на событие `EVENT_OBJECT_SHOW` или смену переднего плана | Список панелей из `WindowManager` без копирования |
| `JapaneseIme.GetRegKanaMd` | Открытие ключа реестра и чтение каждые 200 мс при включённом IME | Кэш значения плюс `RegNotifyChangeKeyValue` |

Всё перечисленное стоит миллисекунды. Это задел под рост числа окон, pins и
записей порядка, а не текущие тормоза.
